# Pro 1. Диета образа

Цель: уменьшить размер образа веб-приложения из lab2/task04
как минимум в 2 раза и доказать это цифрами.

## Сравнение размеров (было -> стало)

| Образ | Базовый образ | Размер | Комментарий |
|---|---|---|---|
| myapp-web:full | python:3.8 | 1.47 ГБ | исходный вариант из lab2/task04: полная база с apt, компиляторами и кэшем |
| myapp-web:before (= latest) | python:3.8-slim | 217 МБ | промежуточный вариант «до» |
| myapp-web:alpine (итог) | python:3.8-alpine | 111 МБ | итоговый вариант «после» |

Уменьшение относительно before: 217 МБ -> 111 МБ (примерно в 2 раза).
Относительно исходного full — в 13.3 раза.

## Чем отличаются базовые образы

| Базовый образ | Дистрибутив | Пакетный менеджер | Что внутри |
|---|---|---|---|
| python:3.8 | Debian | apt | полный дистрибутив: компиляторы, документация, утилиты — 1.47 ГБ |
| python:3.8-slim | Debian (облегчённый) | apt | минимальный Debian без компиляторов и документации |
| python:3.8-alpine | Alpine Linux | apk | musl вместо glibc, busybox вместо coreutils |

Разница между full и slim — почти гигабайт компиляторов, заголовочных
файлов и документации, которые в рантайме не нужны.

## Приёмы оптимизации

1. Базовый образ: переход с python:3.8-slim на python:3.8-alpine.
2. Build-зависимости ставятся временно и удаляются после сборки:

    RUN apk add --no-cache --virtual .build-deps gcc musl-dev postgresql-dev \
        && pip install --no-cache-dir -r requirements.txt \
        && apk del .build-deps

   Проверка, что их нет в финальном образе (вывод пуст — пакетов нет):

    $ docker run --rm myapp-web:alpine sh -c "apk info | grep -E 'gcc|musl-dev'"
    (пусто)

3. Кэш pip: флаг --no-cache-dir запрещает pip хранить скачанные
   wheel-файлы в /root/.cache/pip — экономит несколько десятков МБ.
4. Порядок COPY: сначала requirements.txt, затем pip install, потом
   код приложения — при изменении кода слой с зависимостями не
   пересобирается, срабатывает кэш.
5. .dockerignore: исключает .git, __pycache__, *.pyc, .venv — мусор
   не попадает в контекст сборки и в образ.

## Слои образа (docker history)

    $ docker history myapp-web:alpine

Каждый RUN/COPY/ADD — отдельный слой. CMD и ENV веса не дают (0B),
основной вес несут ADD базового образа, COPY кода и слой pip install.
Поэтому чистка кэша делается в одном RUN: удалённые в следующем слое
файлы всё равно продолжают занимать место в предыдущем.

## musl vs glibc: почему на Alpine иногда всё ломается

Alpine использует libc-реализацию musl вместо стандартной glibc.
Бинарные пакеты (wheel'ы) собраны под glibc, поэтому на Alpine:

- pip не находит готовый wheel и собирает пакет из исходников —
  нужны gcc, musl-dev и заголовки (для psycopg2 — postgresql-dev);
- некоторые бинарные библиотеки падают с ошибками вида
  «Error loading shared library» или крашатся на несовместимых вызовах.

Поэтому для psycopg2 в Dockerfile добавлены build-deps: компилятор
собирает пакет под musl, после чего пакеты сборки удаляются.

## Доказательство работоспособности

    $ docker run --rm myapp-web:alpine python -c "import psycopg2; print('psycopg2 OK')"
    psycopg2 OK

    $ docker compose up -d
    $ curl http://localhost:5001/
    <h1>Users</h1><ul><li>Alice</li><li>Bob</li><li>Charlie</li></ul>

Приложение на самом маленьком образе работает: подключается к
PostgreSQL по имени сервиса db, отдаёт данные из таблицы users
(HTTP 200). Остановка штатная: db — код 0, web — код 137
(SIGKILL после таймаута graceful shutdown, норма для dev-сервера).

## Вывод

Размер образа уменьшен с 217 МБ (before) до 111 МБ (alpine) —
примерно в 2 раза, относительно исходного full (1.47 ГБ) — в 13.3 раза.
Ради размера пожертвовали:

1. комфортной сборкой — вместо apt привычный apk, бинарные пакеты
   приходится собирать через build-deps;
2. совместимостью — musl не всегда берёт готовые wheel'ы;
3. скоростью сборки — компиляция psycopg2 из исходников дольше;
4. утилитами отладки — в Alpine нет привычного набора инструментов
   для диагностики внутри контейнера.
