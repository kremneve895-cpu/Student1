Docker

Контейнеризация с нуля: что это, как работает, что умеет

Основы разработки · теория к лабораторным lab1–lab2

Проблема: «у меня работало»

Знакомая история:

  • у разработчика Python 3.8, на сервере 3.11 — не заводится
  • «поставь вот эти 15 пакетов нужных версий» — инструкция на 3 страницы
  • на Windows работает, на Linux — нет

Причина: приложение — это не только код, но и всё его окружение: интерпретатор, библиотеки, системные пакеты, переменные.

Docker упаковывает код вместе с окружением в стандартную коробку — контейнер.

Аналогия: контейнерные перевозки

До контейнеров грузы возили россыпью: мешки, бочки, ящики — каждый груз по-своему. Потом придумали стандартный контейнер:

  • неважно, что внутри — снаружи стандартная коробка
  • один и тот же кран, корабль, грузовик для любого груза

Docker — то же для программ: неважно, Python там или база данных — любой сервер с Docker умеет это run.

Контейнер — это не «маленькая ВМ», а обычный процесс Linux в изоляции.

Как контейнер изолирован (простыми словами)

  • namespaces — «камера-обскура»: процесс видит свои файлы, свою сеть, свои процессы и думает, что он один в системе
  • cgroups — «счётчик ресурсов»: сколько CPU и памяти можно (pro06)

Отсюда следствия:

  • контейнер на чужой машине ведёт себя одинаково
  • удалил контейнер — система чистая, ничего не «установлено»
  • на одном хосте — десятки сервисов, не мешая друг другу

Три главных сущности

СущностьЧто этоАналогия из ООП

Из одного образа можно запустить сколько угодно контейнеров.

docker pull nginx     # образ: реестр → машина
docker run  nginx     # контейнер: образ → запущенный процесс

  • команда docker — только клиент, работу делает демон
  • поэтому «Cannot connect to the Docker daemon» = Docker Desktop не запущен
  • на macOS/Windows демон живёт внутри маленькой Linux-ВМ — контейнеры всегда Linux

Образы состоят из слоёв

FROM python:3.8-slim   # слой 1: базовая система
WORKDIR /app           # слой 2
COPY app.py .          # слой 3
CMD ["python","app.py"] # слой 4
  • каждая инструкция = новый слой поверх предыдущих
  • слои кэшируются: не изменилось — берётся из кэша (метка CACHED)
  • поэтому изменчивое (код) кладут в конец Dockerfile — проверите сами в task05
  • слои общие между образами: 10 python-образов не съедят место ×10

docker ps        # только живые
docker ps -a     # все, включая остановленные
docker stop web  # остановить (контейнер остаётся)
docker rm web    # удалить совсем
docker logs web  # что он писал в консоль

Важно: контейнер жив, пока жив его главный процесс. Выход из bash = смерть контейнера (task02).

  • базе данных наружу порт обычно не пробрасывают — ходят только соседние контейнеры

Тома: данные вне контейнера

Контейнер удалили — всё внутри пропало. Для данных есть тома:

docker volume create mysql-data
docker run -v mysql-data:/var/lib/mysql mysql:5.7
  • именованный том (mysql-data) — хранится у Docker, для данных (lab1 task06–07)
  • bind mount (-v $(pwd)/app.py:/app.py) — конкретный файл/папка с хоста, для кода при разработке

«Вау-момент» lab1/task07: удаляем контейнер с MySQL, поднимаем новый — база на месте, потому что лежит в томе.

Сети: контейнеры зовут друг друга по имени

docker network create my-network
docker run -d --network my-network --name redis-server redis
  • в пользовательской сети работает DNS по имени контейнера: redis-server вместо IP
  • IP меняются при перезапуске, имена — нет
  • контейнеры в разных сетях друг друга не видят — изоляция

lab1/task09: два Python-контейнера общаются через Redis, зная только его имя.

Docker Compose: оркестр, а не солист

Реальное приложение = несколько контейнеров. Вместо пяти docker run — один файл:

services:
  web:
    build: .              # собрать из Dockerfile
    ports: ["5001:5001"]
    depends_on: [db]      # ждём базу
  db:
    image: postgres:13
    environment: [POSTGRES_PASSWORD=...]
    volumes: [pgdata:/var/lib/postgresql/data]
  • все сервисы автоматически в общей сети и видны по именам (db — это имя сервиса!)
  • docker compose up -d поднимает всё, down — убирает

Как попасть внутрь работающего контейнера

СпособКогда
docker exec -it web bashосновной: «открыть консоль» в живом контейнере
docker logs -f webчитать вывод, не заходя внутрь
SSH в контейнеручебный приём lab2 — в жизни почти не нужен, есть exec

exec запускает дополнительный процесс внутри — поэтому exit из него не убивает контейнер (в отличие от exit из главного процесса в task02).

Реестры образов

  • Docker Hub — публичный реестр: официальные образы (nginx, postgres, redis…)
  • свой образ публикуем: docker tag → docker push (lab2/task06)
  • можно поднять свой registry одной командой (pro07) — «частный Docker Hub»
  • Artifactory из прошлой темы — та же идея, но для любых артефактов

Имя образа = адрес: username/myapp-web:1.0 — кто, что, какая версия.

Что ещё умеет Docker (заглянем в pro)

  • лимиты ресурсов — CPU и память на контейнер (pro06)
  • healthcheck — «жив ли сервис на самом деле» (pro03)
  • multi-stage сборка — образ без компиляторов (pro02)
  • compose override — dev и prod из одной базы (pro09)
  • сборка в CI — GitHub Actions собирает образ на каждый push (pro10)

Безопасность: минимум на сегодня

  • пароли — не в коде и не в git: переменные окружения, секреты CI
  • не публикуйте порты баз данных наружу
  • root внутри контейнера — не «настоящий» root, но лучше non-root пользователь
  • образы из интернета = чужой код: берите официальные (nginx, postgres)

Когда Docker НЕ нужен

  • разовый скрипт на машине, где всё уже стоит
  • жёсткая изоляция (мульти-тенант с недоверием) — там ВМ крепче
  • GUI-приложения, драйверы, «голое железо»

Docker решает задачу упаковки и доставки серверного ПО — и делает это отлично.

Итоги

  • контейнер = код + окружение в стандартной коробке
  • образ — шаблон, контейнер — запущенный экземпляр, реестр — хранилище
  • данные — в томах, связь — через сети по именам
  • Dockerfile собирает образ, Compose поднимает стек
  • одинаково работает у всех — поэтому это стандарт индустрии
